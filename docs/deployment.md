# Deployment

`infra/terraform` stands up the API on ECS Fargate with RDS Postgres behind an ALB.

Validated with `tofu validate` against the AWS provider schema. **Not applied against a
live account** — there is no running deployment behind this repository, and the numbers in
the README come from local runs.

## Shape

```
        internet
            │
      ALB (public subnets, :80)
            │  security group → security group, not CIDR
      ECS Fargate tasks (private subnets, :8000)
            │
      RDS Postgres 16 + pgvector (private subnets, :5432)
            │
      Secrets Manager: database DSN, provider API key
```

Tasks reach the provider API through a single NAT gateway. Per-AZ NAT roughly triples the
standing cost of this stack; losing an AZ degrades outbound synthesis but the service stays
reachable through the ALB, which is the right trade at this size and an easy variable to
flip if it stops being.

## Decisions worth defending

**Two health checks doing different jobs.** The ALB target group checks `/health` —
liveness only. The ECS container check calls `/health/ready`, which reports `degraded` when
the index is empty. A task that is up with nothing indexed should stay visible and alarm,
not quietly leave rotation while the load balancer reports everything healthy. Because the
container check is index-aware and the service has
`deployment_circuit_breaker { rollback = true }`, a deployment that ships a broken ingest
rolls itself back instead of replacing a working one.

**Immutable image tags.** The ECR repository is `IMMUTABLE`, images are tagged with the
commit SHA, and the `api_image` variable rejects anything ending in `:latest`:

```hcl
validation {
  condition     = !endswith(var.api_image, ":latest")
  error_message = "Deploy an immutable tag so a rollback can name the exact prior image."
}
```

A rollback has to be able to name the exact prior image. `:latest` makes that impossible
and makes "which build is running" unanswerable.

**Secrets are never in the image or the task definition.** The execution role pulls the
database DSN and API key from Secrets Manager at task start. The **task** role is empty:
application code has no reason to call AWS, so it is granted nothing. The database password
is generated by Terraform and never leaves state and Secrets Manager.

**Security groups reference groups, not CIDRs.** Postgres accepts connections only from the
API security group; the API accepts only from the ALB's. The rules live in separate
`aws_vpc_security_group_ingress_rule` resources so two groups can reference each other
without a cycle in the graph.

**Deletion protection on by default**, with `skip_final_snapshot` derived from it — the
database holds the index and the evaluation history, and rebuilding it means re-ingesting
the whole corpus.

## Deploying

`.github/workflows/deploy.yml` runs on a successful CI run on `main`. It will not run at
all if CI failed, so **a commit whose evaluation gate is red cannot reach production**.

1. OIDC into the deployment role — no long-lived AWS keys in GitHub.
2. Build and push `…:$GITHUB_SHA` to ECR.
3. Register a new task definition revision with that image and update the service.
4. `aws ecs wait services-stable`. Without this the job goes green on the API call rather
   than on the rollout, so a circuit-breaker rollback would look like a successful deploy.
5. Poll `/health/ready` until it reports `ok`, so the job fails if the service came up
   without a usable index.

### First apply

```bash
cd infra/terraform
tofu init
tofu apply -var="api_image=<account>.dkr.ecr.<region>.amazonaws.com/lexground-prod:<sha>"
```

Chicken-and-egg: the ECR repository is created by the same configuration that needs an
image. Apply once targeting `aws_ecr_repository.api`, push an image, then apply in full.

The index is not created by Terraform. After the first apply, run `lexground init-db` and
`lexground ingest` against the RDS instance from somewhere inside the VPC — a one-off ECS
task on the same cluster is the least ceremony. Until then `/health/ready` reports
`degraded`, which is correct.

### Configuration

Everything is `LEXGROUND_`-prefixed and read by pydantic-settings.

| Variable | Purpose |
|---|---|
| `LEXGROUND_DATABASE_URL` | Async DSN. From Secrets Manager in ECS. |
| `LEXGROUND_ANTHROPIC_API_KEY` | Absent → extractive backend. Present → Claude synthesis. |
| `LEXGROUND_EMBEDDING_BACKEND` | `fastembed` in deployment, `hash` for tests. |
| `LEXGROUND_SYNTHESIS_EFFORT` | Effort level for synthesis. |
| `LEXGROUND_MIN_LEXICAL_SCORE` / `_MIN_DENSE_SIMILARITY` | Answerability backstops. See [evaluation.md](evaluation.md#abstention) before changing either. |

**Changing the embedding backend or model invalidates the whole index.** Every vector has
to be recomputed, and evaluation results either side of that change are not comparable —
which is what `index_version` records.

## What is missing

Honest list of what a real production deployment needs and this does not have:

- **TLS.** The listener is HTTP on :80. Real traffic needs ACM and a redirect, which needs
  a domain this project does not own.
- **Autoscaling.** `desired_count` is fixed. There is no load pattern to scale against yet.
- **Alarm routing.** The CloudWatch alarms on unhealthy targets and 5xx rate have no SNS
  topic behind them.
- **Remote state.** The backend is local, so the configuration is single-operator. A real
  setup needs S3 with DynamoDB locking.
- **A scheduled re-ingest.** Consolidated versions of these acts change; nothing here
  notices.
